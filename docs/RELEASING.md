# Загрузка на GitHub и выпуск

Эта папка — самостоятельный репозиторий. Загружайте только её содержимое. Соседнее оконное приложение DelugeSleep.exe, пароли, пользовательские настройки и резервные копии сюда не входят; EXE/DLL дополнительно исключены в .gitignore.

Репозиторий: https://github.com/GraphGiraffe/deluge-afterdownloads. Ветка интеграции — `dev`, стабильная — `main`. Изменения проходят через рабочую ветку и PR в `dev`, релиз — через отдельный PR из `dev` в `main`; способ слияния — Squash and merge.

1. Создайте рабочую ветку от актуальной `dev`, внесите изменения, обновите документацию и выполните локальные тесты.
2. Отправьте рабочую ветку и создайте PR в `dev`. Коммиты и действия публикации выполняются от имени владельца; личная почта не требуется, можно использовать GitHub noreply.
3. Дождитесь workflow **Test and build**. Он проверяет Python 3.9/3.13/3.14 на Windows и Ubuntu и прикладывает сборки. Это не заменяет проверку переходов питания на реальном компьютере.
4. Проверьте плагин в реальном Deluge, включая dry-run и отмену. Проверьте известные ограничения в TESTING.md.
5. Для выпуска обновите VERSION в build.py, версию диагностики в core.py, CHANGELOG.md и RELEASE_NOTES.md. Версии должны совпадать.
6. После проверки и переноса релизного коммита в `main` создайте на нём аннотированный тег `v1.0.0` и отправьте его: `git tag -a v1.0.0 -m "AfterDownloads 1.0.0"`, затем `git push origin v1.0.0`.
7. Workflow **Build release** сначала тестирует Python 3.9/3.13/3.14 на Windows и Ubuntu, проверяет совпадение версии и тега, собирает `.egg` для Python 3.9–3.14 и SHA256SUMS.txt, затем сохраняет их в artifact `AfterDownloads-v1.0.0-release`.
8. Скачайте artifact, проверьте SHA-256, установите нужный `.egg` и проверьте dry-run в Deluge. Создайте GitHub Release для существующего тега от своего аккаунта, приложите шесть `.egg` и SHA256SUMS.txt, используйте docs/RELEASE_NOTES.md как описание. Проверьте вложения и опубликуйте релиз.

Workflow не включает реальные команды сна/гибернации/выключения в тестах. Проверяется маршрутизация и отмена. Реальный переход питания на чужих компьютерах не гарантируется unit-тестами.

Workflow не публикует релиз от имени github-actions[bot] и имеет только `contents: read`. Локальный build.py также ничего не отправляет на GitHub.
